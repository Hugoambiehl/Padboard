# Releasing Padboard

Versions follow [Semantic Versioning](https://semver.org): `MAJOR.MINOR.PATCH`,
and `MAJOR.MINOR.PATCH-rc.N` for release candidates (published as GitHub
pre-releases). The desktop app, the tablet app and the protocol crates share
one version.

## What a release contains

| File | Built by | Notes |
|---|---|---|
| `Padboard_X_x64-setup.exe` | release workflow (Windows runner) | NSIS installer, English or French from the Windows language, from Padboard's template (`src-tauri/windows/installer.nsi`, see *Notes*). **Not signed** (no Authenticode certificate: SignPath Foundation declined for now): SmartScreen asks for confirmation. |
| `Padboard_X_amd64.deb` | release workflow (Ubuntu 22.04) | Ubuntu 22.04+ / Debian 12+. Package version `X` with `~` instead of `-` for an rc (`0.2.1~rc.1`, see *Notes*). |
| `padboard-X.apk` | release workflow, **signed on the maintainer’s PC** | The workflow attaches `padboard-X-unsigned.apk`; `scripts/sign-release.sh` signs it and replaces it. The keys never leave that PC (`docs/release-signing.md`). |
| `Padboard_X_x64-setup.exe.sig`, `latest.json` | `scripts/sign-release.sh` | The in-app updater (Windows) reads `latest.json` and checks the installer against this signature, made for version X. |
| `SHA256SUMS`, `SHA256SUMS.sig` | release workflow, then `scripts/sign-release.sh` | Written again with the signed files, and signed for version X: the PC checks it before sending the APK to a tablet. |

The release notes are the version's section of `CHANGELOG.md`, generated by
[git-cliff](https://git-cliff.org) (`cliff.toml`) from the Conventional
Commits: only `feat`, `fix` and `perf` are listed. Release candidates fold
into the release that follows them. The first release (0.1.0) has a written
summary instead of its whole development history (`cliff.toml`).

## Steps

Tools (once): `cargo install git-cliff --locked`; the Android SDK build-tools
for `apksigner`; the GitHub CLI (`gh`).

1. **Prepare** on an up-to-date, clean `main` (the CI is green):

   ```sh
   scripts/release.sh 0.1.0-rc.1
   ```

   It sets the version in `Cargo.toml` (+ `Cargo.lock`), `tauri.conf.json`,
   `package.json` (+ lock) and `apps/android/app/version.properties`
   (versionName and a growing versionCode; kept out of the Gradle files so
   CI's Gradle cache survives a version change), regenerates `CHANGELOG.md`, commits
   `chore(release): v0.1.0-rc.1` and creates the annotated tag. Then a
   second commit, `chore: start X.Y.Z-dev`, moves `main` to the next
   development version (the same X.Y.Z after a release candidate,
   X.(Y+1).0 after a release): a build of `main` is never taken for a
   published version (CI: `scripts/check-version.sh`). Nothing is pushed:
   check the commits and the changelog first.

2. **Publish the tag**: `git push origin main v0.1.0-rc.1` (both commits;
   the workflow builds the tag). The **Release**
   workflow checks that the tag matches the version, builds everything and
   creates a **draft** release (`gh run watch` to follow it).

3. **Sign the draft** on your PC (keys: `docs/release-signing.md`):

   ```sh
   scripts/sign-release.sh 0.1.0-rc.1
   ```

   It downloads the draft, checks it against the CI's `SHA256SUMS`, signs
   the APK (and checks its certificate), signs the installer for the
   updater, writes `latest.json`, writes and signs `SHA256SUMS` again,
   checks the result with the app's own code (example `verify-release`),
   then uploads it and removes the unsigned APK. It asks for the update
   key's password once. The APK key's properties are found through
   `PADBOARD_SIGNING`, else `padboard.signing` in
   `~/.gradle/gradle.properties`, else
   `~/.padboard-signing/signing.properties` (the script prints which one;
   0.2.2-rc.1 failed when `gradle.properties` had lost its line, before
   that default existed). If Authenticode signing is added to the workflow
   one day (SignPath declined the first request; it can be asked again
   later), nothing changes here: the installer is final before the draft
   exists, and the script refuses one without its Authenticode signature
   once the workflow has a SignPath step.

4. **Test** the builds (Windows: `docs/windows-test-plan.md`; the tablet:
   `adb install -r padboard-X.apk`, then `docs/tablet-test-plan.md`). A rejected draft is deleted
   (`gh release delete v0.1.0-rc.1`), never re-signed after publishing.

   **Antiviruses**: the installer has no Authenticode signature (SignPath
   Foundation declined the request for now; SmartScreen warns on first
   launch, expected). What to do depends on the version:

   | | VirusTotal check | False positive reports |
   |---|---|---|
   | Release candidate | Before publishing | Bitdefender or Microsoft only if it detects the installer (`STOP:`) or a user reports it blocked |
   | Release | Before publishing | The same; another engine only if its verdict still holds 2 weeks after publishing |

   No systematic submission since 0.2.2 (decided on 2026-11-26): up to
   0.2.1 every release was sent to Bitdefender and Microsoft before
   publishing, detected or not.

   **VirusTotal**, every release and release candidate, before publishing:

   1. Download the signed draft's installer
      (`gh release download vX --pattern 'Padboard_*_x64-setup.exe'`) and
      check its SHA-256 against the draft's `SHA256SUMS`
      (`sha256sum -c --ignore-missing SHA256SUMS`).
   2. Upload it to [virustotal.com](https://www.virustotal.com) (*File*).
      Check that the SHA-256 VirusTotal shows is the same.
   3. Expected: **Bitdefender and Microsoft *Undetected***, and only
      generic verdicts of heuristic or machine learning engines on unknown
      unsigned programs (no family name), **at most 3**: SecureAge *Malicious*,
      CrowdStrike Falcon `Win/grayware_confidence_N%`, DeepInstinct
      *MALICIOUS*, Sophos `Generic ML PUA (PUA)`. Note the result (count,
      engines, SHA-256) in the table below and in the release's notes.
   4. Stop and do not publish before understanding why if Bitdefender or
      Microsoft detects it, if an engine gives a named detection (a family
      name, not a generic heuristic), or if there are more than 3 generic
      verdicts: rebuild nothing yet, look at what changed since the
      previous clean release.

   `verify-release` reads the report too, by the installer's SHA-256
   (nothing is uploaded), when `VIRUSTOTAL_API_KEY` holds the public API
   key of a free VirusTotal account (*API key* in the account menu), kept
   in `~/.config/virustotal-key` (`chmod 600`, outside the repo, never
   committed or printed). Tested with a real key on 2026-11-18
   (0.2.1-rc.1: `VirusTotal: 3/71`, the three engines, the link). After
   the signature and the upload to VirusTotal (step 2):

   ```sh
   gh release download vX -D /tmp/padboard-X
   VIRUSTOTAL_API_KEY=$(cat ~/.config/virustotal-key) \
     cargo run -q -p padboard-desktop --example verify-release -- /tmp/padboard-X X
   rm -r /tmp/padboard-X
   ```

   It prints the detections and engines (with the names of VirusTotal's
   site: the API calls SecureAge `APEX`, shown `SecureAge (APEX)`), and
   `STOP:` lines for Bitdefender, Microsoft or more than 3 detections;
   whether a verdict is generic stays your call. Informative only (exit status unchanged): in
   `sign-release.sh` it says the installer is not on VirusTotal yet.

   **False positive reports to Bitdefender and Microsoft**, only when one
   of them detects the installer (Bitdefender or Microsoft on VirusTotal,
   a `STOP:` line of `verify-release`, step 4) or when a user reports
   Padboard blocked or quarantined by one of them:

   - **Bitdefender**: [bitdefender.com/submit](https://www.bitdefender.com/submit),
     category *False Positive* (detection name if any, e.g.
     `Atc4.Detection`). VirusTotal does not run Bitdefender's behaviour
     detection (ATC): such a detection only shows up through a user (or
     the Windows test plan), and is handled as below.
     **A false positive submission only covers the static detection**
     (Bitdefender's lab answered for 0.2.0-rc.4: static analysis clean).
     For a behaviour detection (ATC), go through **Bitdefender support**
     with a **BDSYS log** (Bitdefender's support tool, run on the Windows
     PC where it was detected), a description of what happened and
     screenshots of the alert and the quarantine. This worked for the ATC
     detection of the rc.2 installer started by Padboard (8.5 of the
     Windows test plan): false positive confirmed and the detection fixed
     on 2026-11-19 (case 1011719053, after the BDSYS log). Scope of the
     fix (their answer for the same case): it targets the behaviour that
     triggered the false positive, so later versions may pass, but
     nothing is guaranteed while Padboard is unsigned. They advise
     submitting every stable installer before publishing: done up to
     0.2.1, no longer systematic since 0.2.2 (only on a detection).
   - **Microsoft**: [Microsoft Security Intelligence](https://www.microsoft.com/en-us/wdsi/filesubmission)
     (sign in with a **personal Microsoft account**: a school or work
     account asks for an administrator's approval), as *Software
     developer*, product *Microsoft Defender Antivirus*, the required
     *Company Name* field: `Padboard (open source project)`, *What do
     you believe this file is?* → *Incorrectly detected as
     malware/malicious*, the installer itself (≤ 50 MB), detection name:
     the one shown, else `None`, and the text below in *Additional
     information* (English, 1,900 characters at most).

     ```text
     Padboard X, installer of an open source (GPL-3.0) desktop app by
     its author. Detected by Microsoft Defender as <detection name>
     (definition version <version>; VirusTotal: <link>), a false
     positive. The installer is an unsigned NSIS
     installer built by GitHub Actions from the public repository
     https://github.com/Hugoambiehl/Padboard (tag vX), SHA-256 <hash>,
     listed in the release's signed SHA256SUMS:
     https://github.com/Hugoambiehl/Padboard/releases/tag/vX
     Padboard turns an Android tablet into a control surface for the PC:
     it sends keyboard shortcuts, controls media, volume, microphone and
     OBS scenes when the user presses a button on the tablet, connected
     by USB (adb) or the local network. No bundled offers, no advertising,
     no telemetry; it only reaches GitHub to check for updates.
     ```

     For a block reported by a user without a detection on VirusTotal,
     replace the second sentence with what the user saw (detection name,
     definition version) and the date.

   - **Other engines** (SecureAge, CrowdStrike Falcon, DeepInstinct,
     Sophos…): only if a generic verdict still holds more than 2 weeks
     after a release is published (a *Reanalyze* on VirusTotal first:
     machine learning models often change in that time). Then report it
     to its maker (the addresses of [VirusTotal's list](https://docs.virustotal.com/docs/false-positive-contacts)),
     in English: the VirusTotal report link, the SHA-256, the release
     page, "open source (GPL-3.0), built by GitHub Actions from
     github.com/Hugoambiehl/Padboard, unsigned NSIS installer". Send the
     link, not the file, unless the maker asks for it: these mailboxes
     often refuse `.exe` and archives.
     - CrowdStrike Falcon (its VirusTotal engine): `VTscanner@crowdstrike.com`.
     - DeepInstinct: `vt-fps-requests@deepinstinct.com`.
     - SecureAge: the form at [secureage.com/contact-us](https://www.secureage.com/contact-us).
     - Sophos: the file through [SophosLabs Intelix](https://intelix.sophos.com)
       (guest mode, no account), marked as a false positive; or by mail,
       `samples@sophos.com`, the installer in a ZIP protected by the
       password `infected` (their procedure for non-customers). Recheck
       the verdict after about 15 days. The mail route worked for
       0.2.1-rc.1: classified as a false positive the same day (case
       03641915). Their fix covers that file's hash only: a later
       version detected again needs a new case, sent the same way.

   Bitdefender's *Advanced Threat Control* quarantined the 0.2.0-rc.2
   installer started by Padboard rc.1, and Padboard with it
   (`docs/windows-test-plan.md`, 8.5): since rc.3 Padboard never starts an
   installer that is not validly signed by `TRUSTED_PUBLISHER`
   (`updates/installer.rs`, empty until SignPath), it shows it in the
   Explorer. `TRUSTED_PUBLISHER` stays empty while there is no
   certificate. If one comes later: set that constant to the certificate's
   name as Windows shows it, check its issuer too, and go back from
   `basicUi` to `passive` (`installMode` in `tauri.conf.json`).

5. **Publish** the draft from the GitHub page (or
   `gh release edit v0.1.0-rc.1 --draft=false`). From then on, the apps
   see it: `latest.json` is read from the latest release (and from
   pre-releases by apps where "Versions de test" is on).

A failed or wrong release candidate is not re-tagged: fix it on `main` and
release `-rc.N+1`.

## Checklist

Copy it into the release's tracking issue (or tick it in your notes) for
every release and release candidate.

Before `scripts/release.sh`:

- [ ] `main` is clean and its CI is green (the Windows job included).
- [ ] Desktop end-to-end tests, all of them:
      `PADBOARD_E2E_HEADLESS=1 scripts/desktop-e2e.sh` (headless; the
      script says the tray tests are skipped).
- [ ] **The tray tests with a real window** (mandatory: headless, they are
      skipped because the virtual display has no tray):
      `scripts/desktop-e2e.sh --no-build e2e/tray`, on a desktop with a
      StatusNotifier host (GNOME: AppIndicator extension). They check the
      icon and its menu over D-Bus; the window close tests are skipped
      (see below), nothing else.
- [ ] **The tray by hand**, accepted while the automatic window close tests
      do not pass with a real window, on the installed build: close the
      window (the explanation shows the first time) → *Masquer* → the icon
      stays and the tablet keeps working → *Ouvrir Padboard* in the tray
      menu → the window comes back → close it again (hidden at once, no
      explanation) → *Quitter Padboard* in the tray menu (the app exits).
- [ ] `scripts/tablet-ui-tests.sh` (tablet UI tests on an emulator at the
      SM-T580's size, e.g. the kiosk exit corner left empty on every screen).
- [ ] `scripts/platform-tools-pin.sh --check` (the "Installer adb" pin is
      Google's newest and current archive: version, size and SHA-1 of the
      index, SHA-256; also run every week by the *Platform-Tools pin*
      workflow). If not, pin it again and check its signatures on Windows.
- [ ] The fastlane changelog of the release's versionCode (releases only).

After `scripts/sign-release.sh`, before publishing:

- [ ] `docs/windows-test-plan.md` on Windows (installer, USB with
      *Installer adb*, actions, tray and startup, update).
- [ ] The `.deb` on clean Ubuntu 22.04 and 24.04 (`apt install ./…deb`
      pulls `adb`).
- [ ] The tablet APK: `adb install -r`, then an update from the PC.
- [ ] `docs/tablet-test-plan.md` on the real tablet (the section of the
      release, e.g. the kiosk exit corner and Android's system gestures).
- [ ] VirusTotal (step 4: Bitdefender and Microsoft undetected, only
      generic heuristic or machine learning verdicts, at most 3), noted in
      the table.
- [ ] Bitdefender or Microsoft detects the installer (`STOP:`), or a
      user reports it blocked: **report it to that one** (step 4, texts
      and links), a behaviour (ATC) detection to Bitdefender support with
      a BDSYS log. Otherwise nothing to submit.
- [ ] Releases only, 2 weeks after publishing: VirusTotal *Reanalyze*;
      a generic verdict still there is reported to its maker (step 4).
- [ ] For a release candidate that follows another: the real update from
      the previous one, with Bitdefender active
      (`docs/windows-test-plan.md`, *Real update with an antivirus*).

## Notes

- **The NSIS template follows the Tauri CLI.** `apps/desktop/src-tauri/
  windows/installer.nsi` is Tauri's `installer.nsi` of the CLI in
  `package-lock.json` (its `; Base:` line), with Padboard's changes
  marked `; Padboard:`: an installed version is always uninstalled as an
  update (`/UPDATE /P`: never *Delete the application data*, the autostart
  `Run` value and the shortcuts kept), after asking to close Padboard;
  the directory page (*Choose Install Location*) is skipped when Padboard
  is installed, whatever the reinstall page's choice (`PadboardSkipDirectory`,
  `$PadboardInstalled` read in `.onInit`), and still shown for a first
  installation;
  Tauri's French strings with typos (`alreadyInstalled`,
  `alreadyInstalledLong`, `newerVersionInstalled`, `older`, `unknown`,
  `choowHowToInstall`, `webview2AbortError`) are replaced by our
  `padboard*` LangStrings (English: Tauri's text), defined after the
  language files. Once Tauri's `French.nsh` is fixed (reported upstream),
  drop them and use Tauri's keys again.
  When `@tauri-apps/cli` is upgraded, `scripts/tests/test_nsis_template.py`
  fails (CI): take the new version's
  `crates/tauri-bundler/src/bundle/windows/nsis/installer.nsi` (tag
  `tauri-cli-vX`), apply the marked changes again, update the `; Base:`
  line, and check an update by hand on Windows (*Désinstaller avant
  d'installer*: no directory page, no checkbox, French texts without
  typos, configuration kept) and a first installation (directory page
  shown).

- **Later: automatic window close tests.** WebKitWebDriver never finishes
  a command whose effect hides the window (and once crashed, segfault,
  when the session ended on a hidden window), and once the window is shown
  again from the tray it sees no element displayed. Idea: an `e2e-control`
  Cargo feature, built only by `desktop-e2e.sh`, active only in test mode,
  closing the window on a signal (`SIGUSR1`: *Masquer*, `SIGUSR2`: the
  window's close button), so no WebDriver command is pending when it
  hides; shipped builds proven without it (a unit test compiled without
  the feature, and the release workflow refusing binaries that contain
  its log marker, as for `test-updates`). Until then:
  `PADBOARD_E2E_TRAY_CLOSE=1` runs the close tests, and the checklist has
  the manual check.

- **Debian versions of release candidates.** Debian reads what follows
  `-` as a package revision, so `0.2.1-rc.1` would sort after `0.2.1` and
  apt would refuse to "downgrade" an rc to the release. From 0.2.1-rc.1
  on, the release workflow gives an rc's `.deb` the Debian version
  `0.2.1~rc.1` (`scripts/deb-version.py`: only the `Version:` line of
  its control file; data untouched), which sorts before `0.2.1` and
  after `0.2.0`; it checks the result with `dpkg-deb -f`. The file name
  keeps the SemVer version (`Padboard_0.2.1-rc.1_amd64.deb`), as do the
  installer, the APK and `latest.json`. `release.sh` prints the Debian
  version. Tested by `scripts/tests/test_deb_version.py`
  (`dpkg --compare-versions`). Packages of earlier rcs (up to
  0.2.0-rc.4) still carry `-rc.N`: installing a release over one of
  them needs `sudo apt install --allow-downgrades ./Padboard_X_amd64.deb`.
- A manual run of the workflow (`gh workflow run Release --ref main`) builds
  the same files as artifacts (7 days), without a release.
- The tablet's store listing (IzzyOnDroid, F-Droid clients) is read from
  `fastlane/metadata/android/<locale>/`: descriptions, screenshots
  (`images/tenInchScreenshots/`, taken on the tablet with a neutral PC
  name: the top bar shows the PC's hostname) and one changelog per
  release, `changelogs/<versionCode>.txt` in English and French, under 500
  characters. Write it before step 1 (no file for release candidates).
  The icon comes from `scripts/icons.mjs`.
