# Releasing Padboard

Versions follow [Semantic Versioning](https://semver.org): `MAJOR.MINOR.PATCH`,
and `MAJOR.MINOR.PATCH-rc.N` for release candidates (published as GitHub
pre-releases). The desktop app, the tablet app and the protocol crates share
one version.

## What a release contains

| File | Built by | Notes |
|---|---|---|
| `Padboard_X_x64-setup.exe` | release workflow (Windows runner) | NSIS installer, English or French from the Windows language. **Not signed** yet (SignPath once public): SmartScreen asks for confirmation. |
| `Padboard_X_amd64.deb` | release workflow (Ubuntu 22.04) | Ubuntu 22.04+ / Debian 12+. |
| `padboard-X.apk` | release workflow, **signed on the maintainer’s PC** | The workflow attaches `padboard-X-unsigned.apk`; `scripts/sign-release.sh` signs it and replaces it. The keys never leave that PC (`docs/release-signing.md`). |
| `Padboard_X_x64-setup.exe.sig`, `latest.json` | `scripts/sign-release.sh` | The in-app updater (Windows) reads `latest.json` and checks the installer against this signature, made for version X. |
| `SHA256SUMS`, `SHA256SUMS.sig` | release workflow, then `scripts/sign-release.sh` | Written again with the signed files, and signed for version X: the PC checks it before sending the APK to a tablet. |

The release notes are the version's section of `CHANGELOG.md`, generated by
[git-cliff](https://git-cliff.org) (`cliff.toml`) from the Conventional
Commits: only `feat`, `fix` and `perf` are listed. Release candidates fold
into the release that follows them. The first release (0.1.0) has a written
summary instead of its whole development history (`cliff.toml`).

## Steps

Tools (once): `cargo install git-cliff --locked`; the Android SDK build-tools
for `apksigner`; the GitHub CLI (`gh`).

1. **Prepare** on an up-to-date, clean `main` (the CI is green):

   ```sh
   scripts/release.sh 0.1.0-rc.1
   ```

   It sets the version in `Cargo.toml` (+ `Cargo.lock`), `tauri.conf.json`,
   `package.json` (+ lock) and `app/build.gradle.kts` (versionName and a
   growing versionCode), regenerates `CHANGELOG.md`, commits
   `chore(release): v0.1.0-rc.1` and creates the annotated tag. Then a
   second commit, `chore: start X.Y.Z-dev`, moves `main` to the next
   development version (the same X.Y.Z after a release candidate,
   X.(Y+1).0 after a release): a build of `main` is never taken for a
   published version (CI: `scripts/check-version.sh`). Nothing is pushed:
   check the commits and the changelog first.

2. **Publish the tag**: `git push origin main v0.1.0-rc.1` (both commits;
   the workflow builds the tag). The **Release**
   workflow checks that the tag matches the version, builds everything and
   creates a **draft** release (`gh run watch` to follow it).

3. **Sign the draft** on your PC (keys: `docs/release-signing.md`):

   ```sh
   scripts/sign-release.sh 0.1.0-rc.1
   ```

   It downloads the draft, checks it against the CI's `SHA256SUMS`, signs
   the APK (and checks its certificate), signs the installer for the
   updater, writes `latest.json`, writes and signs `SHA256SUMS` again,
   checks the result with the app's own code (example `verify-release`),
   then uploads it and removes the unsigned APK. It asks for the update
   key's password once. Once SignPath signs the installer in the workflow
   (Authenticode), nothing changes here: the installer is final before the
   draft exists, and the script refuses one without its Authenticode
   signature.

4. **Test** the builds (Windows: `docs/windows-test-plan.md`; the tablet:
   `adb install -r padboard-X.apk`, then `docs/tablet-test-plan.md`). A rejected draft is deleted
   (`gh release delete v0.1.0-rc.1`), never re-signed after publishing.

   **Antiviruses**, while the installer is not signed (Authenticode): before
   publishing, upload the signed draft's `Padboard_X_x64-setup.exe` to
   [VirusTotal](https://www.virustotal.com) (below) and, if Bitdefender
   detects it there or on Windows, submit it as a false positive
   ([bitdefender.com/submit](https://www.bitdefender.com/submit),
   category *False Positive*, detection name if any, e.g. `Atc4.Detection`),
   so the first users do not meet a detection. Bitdefender's *Advanced
   Threat Control* quarantined a test installer started by the updater (see
   `docs/install-windows.md`, *If your antivirus blocks Padboard*). That is
   why the updater opens the installer as a wizard (`installMode`
   `basicUi` in `tauri.conf.json`) instead of the passive mode: go back to
   `passive` once SignPath signs the installer.

   **VirusTotal**, step by step:

   1. Download the signed draft's installer
      (`gh release download vX --pattern 'Padboard_*_x64-setup.exe'`) and
      check its SHA-256 against the draft's `SHA256SUMS`
      (`sha256sum -c --ignore-missing SHA256SUMS`).
   2. Upload it to [virustotal.com](https://www.virustotal.com) (*File*).
      Check that the SHA-256 VirusTotal shows is the same.
   3. Expected: **Bitdefender and Microsoft *Undetected***, and no more
      than a lone heuristic verdict on unknown unsigned programs. For
      0.2.0-rc.1: 1/70, SecureAge *Malicious* (its heuristic on unknown
      unsigned executables), every other engine *Undetected*. Note the
      result (count, engines, SHA-256) in the release's notes.
   4. Stop and do not publish if Bitdefender or Microsoft detects it, or if
      an engine gives a named detection (a family name, not a generic
      heuristic): rebuild nothing yet, look at what changed since the
      previous clean release.

   And on Windows, Bitdefender active with no exception for Padboard
   (`docs/windows-test-plan.md`, section 7): nothing detected during the
   download, the installation, the first launch watched for 5 minutes,
   *Installer adb* and the first run of `adb.exe` (seen with 0.2.0-rc.1).

5. **Publish** the draft from the GitHub page (or
   `gh release edit v0.1.0-rc.1 --draft=false`). From then on, the apps
   see it: `latest.json` is read from the latest release (and from
   pre-releases by apps where "Versions de test" is on).

A failed or wrong release candidate is not re-tagged: fix it on `main` and
release `-rc.N+1`.

## Checklist

Copy it into the release's tracking issue (or tick it in your notes) for
every release and release candidate.

Before `scripts/release.sh`:

- [ ] `main` is clean and its CI is green (the Windows job included).
- [ ] Desktop end-to-end tests, all of them:
      `PADBOARD_E2E_HEADLESS=1 scripts/desktop-e2e.sh` (headless; the
      script says the tray tests are skipped).
- [ ] **The tray tests with a real window** (mandatory: headless, they are
      skipped because the virtual display has no tray):
      `scripts/desktop-e2e.sh --no-build e2e/tray`, on a desktop with a
      StatusNotifier host (GNOME: AppIndicator extension). They check the
      icon and its menu over D-Bus; the window close tests are skipped
      (see below), nothing else.
- [ ] **The tray by hand**, accepted while the automatic window close tests
      do not pass with a real window, on the installed build: close the
      window (the explanation shows the first time) → *Masquer* → the icon
      stays and the tablet keeps working → *Ouvrir Padboard* in the tray
      menu → the window comes back → close it again (hidden at once, no
      explanation) → *Quitter Padboard* in the tray menu (the app exits).
- [ ] `scripts/tablet-ui-tests.sh` (tablet UI tests on an emulator at the
      SM-T580's size, e.g. the kiosk exit corner left empty on every screen).
- [ ] `scripts/platform-tools-pin.sh --check` (the "Installer adb" pin is
      Google's newest; if not, pin it and check it on Windows).
- [ ] The fastlane changelog of the release's versionCode (releases only).

After `scripts/sign-release.sh`, before publishing:

- [ ] `docs/windows-test-plan.md` on Windows (installer, USB with
      *Installer adb*, actions, tray and startup, update).
- [ ] The `.deb` on clean Ubuntu 22.04 and 24.04 (`apt install ./…deb`
      pulls `adb`).
- [ ] The tablet APK: `adb install -r`, then an update from the PC.
- [ ] `docs/tablet-test-plan.md` on the real tablet (the section of the
      release, e.g. the kiosk exit corner and Android's system gestures).
- [ ] VirusTotal (step 4: Bitdefender and Microsoft undetected, at most a
      lone heuristic such as SecureAge's) and Bitdefender's false positive
      form for the installer if it detected anything.
- [ ] For a release candidate that follows another: the real update from
      the previous one, with Bitdefender active
      (`docs/windows-test-plan.md`, *Real update with an antivirus*).

## Notes

- **Later: automatic window close tests.** WebKitWebDriver never finishes
  a command whose effect hides the window (and once crashed, segfault,
  when the session ended on a hidden window), and once the window is shown
  again from the tray it sees no element displayed. Idea: an `e2e-control`
  Cargo feature, built only by `desktop-e2e.sh`, active only in test mode,
  closing the window on a signal (`SIGUSR1`: *Masquer*, `SIGUSR2`: the
  window's close button), so no WebDriver command is pending when it
  hides; shipped builds proven without it (a unit test compiled without
  the feature, and the release workflow refusing binaries that contain
  its log marker, as for `test-updates`). Until then:
  `PADBOARD_E2E_TRAY_CLOSE=1` runs the close tests, and the checklist has
  the manual check.

- Debian sorts `0.1.0-rc.1` after `0.1.0`: installing the final `.deb` over a
  release candidate needs `sudo apt install --allow-downgrades ./Padboard_0.1.0_amd64.deb`.
- A manual run of the workflow (`gh workflow run Release --ref main`) builds
  the same files as artifacts (7 days), without a release.
- The tablet's store listing (IzzyOnDroid, F-Droid clients) is read from
  `fastlane/metadata/android/<locale>/`: descriptions, screenshots
  (`images/tenInchScreenshots/`, taken on the tablet with a neutral PC
  name: the top bar shows the PC's hostname) and one changelog per
  release, `changelogs/<versionCode>.txt` in English and French, under 500
  characters. Write it before step 1 (no file for release candidates).
  The icon comes from `scripts/icons.mjs`.
