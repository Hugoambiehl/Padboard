# Releasing Padboard

Versions follow [Semantic Versioning](https://semver.org): `MAJOR.MINOR.PATCH`,
and `MAJOR.MINOR.PATCH-rc.N` for release candidates (published as GitHub
pre-releases). The desktop app, the tablet app and the protocol crates share
one version.

## What a release contains

| File | Built by | Notes |
|---|---|---|
| `Padboard_X_x64-setup.exe` | release workflow (Windows runner) | NSIS installer, English or French from the Windows language. **Not signed** yet (SignPath once public): SmartScreen asks for confirmation. |
| `Padboard_X_amd64.deb` | release workflow (Ubuntu 22.04) | Ubuntu 22.04+ / Debian 12+. |
| `padboard-X.apk` | release workflow, **signed on the maintainer’s PC** | The workflow attaches `padboard-X-unsigned.apk`; the maintainer signs it with `scripts/sign-apk.sh` and attaches it. The key never leaves that PC (`docs/android-release.md`). |
| `SHA256SUMS` | release workflow | The signed APK replaces the unsigned one by hand (step 5). |

The release notes are the version's section of `CHANGELOG.md`, generated by
[git-cliff](https://git-cliff.org) (`cliff.toml`) from the Conventional
Commits: only `feat`, `fix` and `perf` are listed. Release candidates fold
into the release that follows them. The first release (0.1.0) has a written
summary instead of its whole development history (`cliff.toml`).

## Steps

Tools (once): `cargo install git-cliff --locked`; the Android SDK build-tools
for `apksigner`.

1. **Prepare** on an up-to-date, clean `main` (the CI is green):

   ```sh
   scripts/release.sh 0.1.0-rc.1
   ```

   It sets the version in `Cargo.toml` (+ `Cargo.lock`), `tauri.conf.json`,
   `package.json` (+ lock) and `app/build.gradle.kts` (versionName and a
   growing versionCode), regenerates `CHANGELOG.md`, commits
   `chore(release): v0.1.0-rc.1` and creates the annotated tag. Nothing is
   pushed: check the commit and the changelog first.

2. **Publish the tag**: `git push origin main v0.1.0-rc.1`. The **Release**
   workflow checks that the tag matches the version, builds everything and
   creates a **draft** release (`gh run watch` to follow it).

3. **Sign the APK** on your PC:

   ```sh
   gh release download v0.1.0-rc.1 -p '*-unsigned.apk' -D /tmp/padboard-release
   scripts/sign-apk.sh /tmp/padboard-release/padboard-0.1.0-rc.1-unsigned.apk
   ```

   It prints the certificate's SHA-256: it must be the one in
   `docs/android-release.md`.

4. **Test** the builds (Windows: `docs/windows-test-plan.md`; the tablet:
   `adb install -r padboard-X.apk`).

5. **Attach the signed APK** and its checksum, remove the unsigned one:

   ```sh
   cd /tmp/padboard-release
   gh release download v0.1.0-rc.1 -p SHA256SUMS
   sed -i '/-unsigned\.apk$/d' SHA256SUMS
   sha256sum padboard-0.1.0-rc.1.apk >> SHA256SUMS
   gh release upload v0.1.0-rc.1 padboard-0.1.0-rc.1.apk SHA256SUMS --clobber
   gh release delete-asset v0.1.0-rc.1 padboard-0.1.0-rc.1-unsigned.apk -y
   ```

6. **Publish** the draft from the GitHub page (or
   `gh release edit v0.1.0-rc.1 --draft=false`).

A failed or wrong release candidate is not re-tagged: fix it on `main` and
release `-rc.N+1`.

## Notes

- Debian sorts `0.1.0-rc.1` after `0.1.0`: installing the final `.deb` over a
  release candidate needs `sudo apt install --allow-downgrades ./Padboard_0.1.0_amd64.deb`.
- A manual run of the workflow (`gh workflow run Release --ref main`) builds
  the same files as artifacts (7 days), without a release.
