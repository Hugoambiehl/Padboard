# Releasing Padboard

Versions follow [Semantic Versioning](https://semver.org): `MAJOR.MINOR.PATCH`,
and `MAJOR.MINOR.PATCH-rc.N` for release candidates (published as GitHub
pre-releases). The desktop app, the tablet app and the protocol crates share
one version.

## What a release contains

| File | Built by | Notes |
|---|---|---|
| `Padboard_X_x64-setup.exe` | release workflow (Windows runner) | NSIS installer, English or French from the Windows language. **Not signed** yet (SignPath once public): SmartScreen asks for confirmation. |
| `Padboard_X_amd64.deb` | release workflow (Ubuntu 22.04) | Ubuntu 22.04+ / Debian 12+. |
| `padboard-X.apk` | release workflow, **signed on the maintainer’s PC** | The workflow attaches `padboard-X-unsigned.apk`; `scripts/sign-release.sh` signs it and replaces it. The keys never leave that PC (`docs/release-signing.md`). |
| `Padboard_X_x64-setup.exe.sig`, `latest.json` | `scripts/sign-release.sh` | The in-app updater (Windows) reads `latest.json` and checks the installer against this signature, made for version X. |
| `SHA256SUMS`, `SHA256SUMS.sig` | release workflow, then `scripts/sign-release.sh` | Written again with the signed files, and signed for version X: the PC checks it before sending the APK to a tablet. |

The release notes are the version's section of `CHANGELOG.md`, generated by
[git-cliff](https://git-cliff.org) (`cliff.toml`) from the Conventional
Commits: only `feat`, `fix` and `perf` are listed. Release candidates fold
into the release that follows them. The first release (0.1.0) has a written
summary instead of its whole development history (`cliff.toml`).

## Steps

Tools (once): `cargo install git-cliff --locked`; the Android SDK build-tools
for `apksigner`; the GitHub CLI (`gh`).

1. **Prepare** on an up-to-date, clean `main` (the CI is green):

   ```sh
   scripts/release.sh 0.1.0-rc.1
   ```

   It sets the version in `Cargo.toml` (+ `Cargo.lock`), `tauri.conf.json`,
   `package.json` (+ lock) and `app/build.gradle.kts` (versionName and a
   growing versionCode), regenerates `CHANGELOG.md`, commits
   `chore(release): v0.1.0-rc.1` and creates the annotated tag. Nothing is
   pushed: check the commit and the changelog first.

2. **Publish the tag**: `git push origin main v0.1.0-rc.1`. The **Release**
   workflow checks that the tag matches the version, builds everything and
   creates a **draft** release (`gh run watch` to follow it).

3. **Sign the draft** on your PC (keys: `docs/release-signing.md`):

   ```sh
   scripts/sign-release.sh 0.1.0-rc.1
   ```

   It downloads the draft, checks it against the CI's `SHA256SUMS`, signs
   the APK (and checks its certificate), signs the installer for the
   updater, writes `latest.json`, writes and signs `SHA256SUMS` again,
   checks the result with the app's own code (example `verify-release`),
   then uploads it and removes the unsigned APK. It asks for the update
   key's password once. Once SignPath signs the installer in the workflow
   (Authenticode), nothing changes here: the installer is final before the
   draft exists, and the script refuses one without its Authenticode
   signature.

4. **Test** the builds (Windows: `docs/windows-test-plan.md`; the tablet:
   `adb install -r padboard-X.apk`). A rejected draft is deleted
   (`gh release delete v0.1.0-rc.1`), never re-signed after publishing.

5. **Publish** the draft from the GitHub page (or
   `gh release edit v0.1.0-rc.1 --draft=false`). From then on, the apps
   see it: `latest.json` is read from the latest release (and from
   pre-releases by apps where "Versions de test" is on).

A failed or wrong release candidate is not re-tagged: fix it on `main` and
release `-rc.N+1`.

## Notes

- Debian sorts `0.1.0-rc.1` after `0.1.0`: installing the final `.deb` over a
  release candidate needs `sudo apt install --allow-downgrades ./Padboard_0.1.0_amd64.deb`.
- A manual run of the workflow (`gh workflow run Release --ref main`) builds
  the same files as artifacts (7 days), without a release.
- The tablet's store listing (IzzyOnDroid, F-Droid clients) is read from
  `fastlane/metadata/android/<locale>/`: descriptions, screenshots
  (`images/tenInchScreenshots/`, taken on the tablet with a neutral PC
  name: the top bar shows the PC's hostname) and one changelog per
  release, `changelogs/<versionCode>.txt` in English and French, under 500
  characters. Write it before step 1 (no file for release candidates).
  The icon comes from `scripts/icons.mjs`.
